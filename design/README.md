# 仕様書ひな型（Spec-Driven Development）

仕様駆動開発のための仕様書テンプレート一式です。
「何を(What)/なぜ(Why)」を記述し、「どう作るか(How)」は実装に委ねます。仕様がそのまま受け入れ基準・E2Eテストの根拠になることを目指します。

## ファイル構成

### 基本（どのプロジェクトでも使う）

| ファイル | 役割 | 単位 |
|---|---|---|
| `HANDOFF.md` | 進捗/確定事項/再開ポイント/残課題（**最初に作り常時更新**） | プロジェクトに1つ |
| `01_requirements.md` | 要件定義（目的・対象ユーザー・課題） | プロジェクトに1つ |
| `02_usecases.md` | ユースケース／ユーザーストーリー | プロジェクトに1つ |
| `03_screen_spec.md` | 画面仕様（UI/UX）テンプレート | **画面ごとにコピーして使う** |
| `04_acceptance_criteria.md` | 受け入れ基準（Given/When/Then） | 機能/画面ごとに追記 |
| `05_non_functional.md` | 非機能要件 | プロジェクトに1つ |
| `06_design_tokens.md` | デザイントークン（色・余白・フォント） | プロジェクトに1つ |
| `00_traceability.md` | F↔US↔AC↔画面↔docs の対応表 | プロジェクトに1つ |

### 追加（データ量が多い／ドメインロジック／実行ランタイムがある場合）

| ファイル | 役割 | いつ作るか |
|---|---|---|
| `07_data_model.md` | データ種別のフィールド定義＋共有構造＋参照関係マップ | データが多いとき |
| `08_domain_logic.md` | 中核となる計算・規則（例：戦闘/料金計算）。複数なら `08_*` を複数 | 固有ロジックがあるとき |
| `09_runtime_spec.md` | 実行系がデータをどう解釈・実行するか（実行意味論・セーブモデル等） | データ駆動の実行系があるとき |
| `10_standard_ui.md` | 実行系が提供する標準UI（標準提供＋テーマ調整） | 標準UIを提供するとき |

> 進め方の全体像・判断の型・チェックリストは `../../spec_driven_migration_playbook.md` を参照。

## 使い方

1. テンプレ一式を新プロジェクトの `design/` にコピーし、各ファイルの `<...>` を埋める。
2. **HANDOFF.md を最初に作成**し、全フェーズで更新し続ける。
3. 画面を追加するたびに `03_screen_spec.md` を `screen_<画面名>.md` としてコピーして記述する。
4. 図は mermaid、文章は markdown で記述する。
5. 受け入れ基準は Given/When/Then で書き、そのままE2Eテストへ落とし込む。
6. 機能を追加/統合/削除したら `00_traceability.md` を同期する。
7. データが多い／固有ロジック／実行ランタイムがあれば 07〜10 を追加で起こす。

## 記述の原則

- 実装手段（フレームワーク・関数名など）は書かない。
- UIは「レイアウト＋状態の列挙＋イベント表＋遷移図」で記述する。
- 状態（空/読込中/正常/エラー/検証エラー）を必ず網羅する。
- エラーメッセージの文言は仕様に直接確定して書く。
